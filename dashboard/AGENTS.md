## 1. Agent Overview & Dashboard Role

The **Invoice Ledger & Financial Presentation Agent** is focused strictly on the **frontend presentation layer**. Invoices are processed OCR documents generated by upstream ingestion pipelines.

The primary goal of this dashboard and agent is to present processed financial invoice data in a clean, intuitive, and human-friendly interface, enable manual status updates (`PENDING` → `PAID`), color-code deadline urgency, and monitor auto-debit bank deductions for cash flow clarity. The `raw_json` field is retained strictly for data backup and deep inspection when needed.

## 2. Model Skills

### Skill 1: `processed_invoice_presenter`
- **Description**: Formats, normalizes, and renders already-processed financial invoice data from Supabase / sample JSON payloads into structured UI views.
- **Inputs**: Normalised Supabase record fields (`property_id`, `billing_purpose`, `total`, `deadline_due`, `filename`, `status`, `payment_method`, `fileID`, `raw_json`).
- **Outputs**: Granular financial table views, property grouping, and Yen currency formatting.

### Skill 2: `urgency_priority_evaluator`
- **Description**: Evaluates payment deadlines against current time and assigns urgency color tiers:
  - Red (Overdue / Due Now): ≤ 0 days remaining until `deadline_due`.
  - Yellow (Upcoming): 1–7 days remaining until `deadline_due`.
  - Blue (Low Priority): > 7 days remaining until `deadline_due`.
  - Green (Paid): Payment completed (`status = 'Paid'` / `'PAID'`).
  - Grey (Archived): Archived or inactive invoice (`status = 'Archived'`).

### Skill 3: `status_mutation_engine`
- **Description**: Provides an effortless human-in-the-loop interactive control to toggle invoice statuses (`PENDING` ↔ `PAID` / `ARCHIVED`) with optimistic UI state updates and Supabase database synchronization.

### Skill 4: `auto_debit_ledger_tracker`
- **Description**: Isolates automated bank deduction transactions (`status = 'Auto-Deducted'` or `payment_method = 'Auto-Debit'` / `'Auto-Deducted'`) from manual checkbook payments to display clear cash flow charts.

### Skill 5: `web-dev-optimization`
- **Description**: Audits and optimizes the web application for Core Web Vitals (INP, LCP, CLS), bundle size, React re-renders, Recharts performance, and Supabase query efficiency. Use when asked to make the site faster, reduce load times, or fix lag.

#### Web Performance & Frontend Optimization Protocol
When executing optimization tasks, perform a structured 5-stage audit and implementation process. Follow these specific rules for Next.js 16, React 19, Vanilla CSS, TypeScript, and Supabase.

**Stage 1 — Diagnostics & Initial Audit**
- Identify components marked `'use client'` that could be converted to React Server Components (RSC).
- Look for heavy libraries (e.g., Recharts, dynamic icons) imported on the critical render path.
- Scan for missing `useMemo`/`useCallback` dependencies, state duplication, or unthrottled search inputs.
- Check if Supabase queries use `select('*')` instead of fetching only required columns.

**Stage 2 — Rendering Architecture (Next.js 16 & React 19)**
- Keep the component tree server-first by default.
- Push `'use client'` boundaries down to the smallest possible leaf node.
- Lazy-load Recharts via `next/dynamic` with `ssr: false` to eliminate server-side chart overhead.
- All derived calculations (filtered lists, Yen sums, urgency aggregates) must be inside `useMemo` with accurate dependency arrays.
- All mutation handlers (status toggle, property assignment) must be `useCallback` to prevent child re-renders.

**Stage 3 — Data Overload & Clutter Prevention**
Any component that renders a list, table, or card collection from dynamic data **must** implement at least one of:
- **Pagination**: Default page size of 10–25 rows; never render unbounded lists. Show `Page X of Y` + Previous/Next controls.
- **Date Range Filter**: Provide time-period filtering (This Week / This Month / Last 3 Months / This Year / All Time) as default.
- **Row Limits + Lazy Loading**: For summary/overview panels, cap visible items (e.g., show top 5 overdue, show top 10 by cost) with a "View All" link to the full Invoices tab.
- **Aggregation over Enumeration**: Prefer showing total counts and sums in summary cards rather than rendering all individual rows. Only enumerate rows where user explicitly navigates to a detail view.
- This principle applies to all tabs including Analysis, Auto-Debit Ledger, and Unassigned Properties as data volume grows continuously.

**Stage 4 — Verified Optimizations Applied in this Project**
The following approaches were confirmed to produce measurable performance improvements:
- **Single-mount data fetch**: `useEffect` with a mounted flag loads invoices exactly once on page load. No background polling intervals.
- **Memoized urgency calculations**: `redCount`, `yellowCount`, `greenSum`, `pendingTotalSum`, etc. are computed once per `invoices` reference change via `useMemo([invoices])`, not on every render.
- **Optimistic UI status updates**: `handleToggleStatus` updates local React state immediately before the async Supabase/API call, making checkbox interactions feel instant.
- **SVG icon components over emoji**: Replaced all emoji characters with inline SVG components. Eliminates browser Unicode fallback rendering overhead and produces consistent cross-platform display.
- **No real-time subscriptions**: Supabase real-time subscriptions are intentionally disabled. This is a "check-in and leave" application, not a live feed dashboard. Eliminates unnecessary WebSocket overhead.
- **Sample file persistence API route**: `/api/mutate-sample` server-side route writes mutations to `samples/Invoice Data_rows.json` on disk, simulating database persistence without a live Supabase connection during development.

**Stage 5 — Verification**
Before marking any optimization task complete:
1. Run `npx tsc --noEmit` — must produce zero type errors.
2. Run `npm run build` — must compile cleanly with zero warnings or errors.
3. **Do NOT start or test the dev server yourself.** Request the user to run `npm run dev` and verify in their browser.

## 3. Model Limits & Guardrails

> [!WARNING]
> **Operational Limits & Execution Boundaries**

1. **No Ingestion Scope**: The agent DOES NOT perform raw OCR document parsing or file upload ingestion. It receives already-processed invoice records.
2. **Schema Integrity**: Queries and mutations strictly conform to the Supabase `invoice_data` table schema:
   - `id` (integer / uuid primary key)
   - `created_at` (timestamp)
   - `property_id` (text / null)
   - `billing_purpose` (text)
   - `total` (numeric / integer JPY)
   - `deadline_due` (date string)
   - `status` (`PENDING` / `Pending` | `PAID` / `Paid` | `Archived` | `Auto-Deducted`)
   - `payment_method` (`To Be Paid Manually` | `Auto-Deducted` | `Credit Card` | `Bank Transfer`)
   - `fileID` (text)
   - `filename` (text)
   - `raw_json` (jsonb / json text backup)

3. **Financial Precision**: All totals are formatted in Japanese Yen (JPY / ¥) as exact integer values.

4. **No Self-Testing**: Agents **must not** attempt to start, restart, or test the development server (`npm run dev`, `next dev`, or any equivalent). When a bug is fixed, present the fix clearly and instruct the user to test it themselves in their browser.

5. **Data Volume Awareness**: All UI components that render collections of records must implement pagination, date-range filtering, or row-capping. Never render an unbounded list from a continuously growing dataset.
