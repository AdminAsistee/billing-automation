# Billing Automation

This is a project to automate invoice document scanning workflow to reduce manual input.
Currently, there is the container backend program and the Dashboard modules which are
distinct pieces of the pipeline.

The container backend utilizes Google Cloud Run, Gemini, Drive, and Supbase to 
extract data from invoice pdfs and insert into a central database. This program
is the backbone of the pipeline being able to run within the cloud, available
whenever a new document has been scanned.

The other module is the Dashboard which presents the data in a digestible manner
and enables analysis capabilities.

# Billing Automation Project Report

This report summarizes the specifications, architecture, and instructions for utilizing the Billing Automation project based on the provided documentation.

## 1. Project Overview

The **Billing Automation** project is an intelligent document processing pipeline designed to automate invoice scanning workflows and minimize manual data entry. It processes financial documents (like Japanese utility bills and tax invoices) and presents the aggregated data in a clean, human-friendly dashboard.

The pipeline comprises two distinct modules:
- **Container Backend**: The processing backbone hosted on Google Cloud Run.
- **Dashboard**: A Next.js frontend for financial presentation and analysis.

**Required Environment Variables**
The software is designed to be modular and configurable entirely through environment variables, requiring no direct code changes to adapt to different environments.
* **Backend (`.env`)**: `GENAI_KEY`, `SUPA_KEY`, `SUPA_URL`, `SUPA_TABLE`, `PORT`, `GOOGLE_AUTH_FILE`.
* **Dashboard (`.env.local`)**: `SUPA_URL`, `PUBLIC_SUPA_ANON_KEY`, `SUPA_DATA_TABLE_NAME`, `SUPA_MASTERLIST_TABLE_NAME`.

> [!NOTE]
> The overarching workflow involves scanning documents to Google Drive, which triggers a Google Apps Script. This script forwards the document to the Container Backend (where Gemini performs OCR) and finally stores the structured JSON payload into a Supabase database.

## 2. System Architecture & Specifications

### 2.1 The Container Backend (Ingestion & Processing)
The backend is a stateless container designed for deployment in Google Cloud Run. It listens for webhook events and processes incoming documents.

- **Stack**: Python, Flask, Google Gemini API, Supabase API.
- **Functionality**:
  - Receives uploaded PDFs.
  - Extracts key data via Gemini OCR (multilingual support, outputs English).
  - Pushes a structured JSON payload to Supabase (`Invoice Data` table).
- **Extracted Data Points**: Property/Unit ID, Billing Purpose, Financial Total (JPY), Deadline, Status, Payment Method, and a raw JSON backup.

### 2.2 The Dashboard (Presentation & Operations)
The dashboard operates purely on the presentation layer, consuming the structured data generated by the backend and stored in Supabase.

- **Stack**: Next.js 16.2.3 (App Router), React 19, TypeScript, Vanilla CSS (no Tailwind), Recharts.
- **Key Features**:
  - **Urgency Timeline**: Color-codes deadlines (Red for overdue/now, Yellow for 1-7 days, Blue for >7 days, Green for paid).
  - **Auto-Debit Ledger**: Visualizes bank deductions separately from manual payments using Recharts.
  - **Status Mutation**: Provides optimistic UI updates to instantly toggle invoices from `PENDING` to `PAID`.
  - **Performance Optimized**: Uses single-mount data fetching, memoized calculations (`useMemo`), and lazy loading for Recharts components to maintain strict Core Web Vitals (CWV) compliance.

## 3. How to Utilize the Programs

### 3.1 Scanning and Triggering the Pipeline
1. Scan documents using the designated office scanner (e.g., JDL fi-8170) equipped with PaperStream Capture.
2. Ensure the destination folder is synced with Google Drive.
3. Once a PDF is saved, Google Apps Script automatically moves it to an Archive folder and forwards it to the Container Backend for OCR processing.

### 3.2 Setting Up the Container Backend
The container backend is built with Python and Flask. While it runs in Google Cloud Run in production, it can be executed locally for testing.

**Local Testing Setup:**
1. Navigate to the `container_backend` directory.
2. Define `.env` variables: `GENAI_KEY`, `SUPA_KEY`, `SUPA_URL`, `SUPA_TABLE`, `PORT`, and `GOOGLE_AUTH_FILE`.
   > [!IMPORTANT]
   > When testing locally with a JSON key file, you **must** uncomment the local JSON auth code and comment out the default Cloud Authentication code. They are mutually exclusive.
   
   *In `config.py`:*
   ```python
   # Uncomment below for local authentication (JSON file)
   # --- GOOGLE SERVICE ACCOUNT KEY FILE ---
   GOOGLE_AUTH = os.getenv("GOOGLE_AUTH_FILE")
   ```

   *In `external_api.py`:*
   ```python
   # Uncomment below for Local Authentication using JSON file
   SERVICE_ACCOUNT_FILE = config.GOOGLE_AUTH
   auth = service_account.Credentials.from_service_account_file(
           SERVICE_ACCOUNT_FILE, scopes=SCOPES)
   
   # IMPORTANT: Comment out the Cloud Authentication below
   # auth, _ = google.auth.default(scopes=SCOPES)
   ```
3. Launch the server: `python3 src/main.py`.
4. Test the webhook locally:
   ```bash
   curl -X POST http://127.0.0.1:5000/webhook -H "Content-Type: application/json" -d "{TEST PAYLOAD HERE}"
   ```

**Google Cloud Run Deployment Setup:**
Ensure your service account is properly configured and secrets are available in Google Secret Manager.

*Option A: Deploying from Source*
```bash
gcloud run deploy autobilling-service \
  --source . \
  --region asia-northeast1 \
  --service-account SERVICE_EMAIL_ACCOUNT_HERE \
  --set-secrets GENAI_KEY=GENAI_KEY:latest,SUPA_URL=SUPA_URL:latest,SUPA_KEY=SUPA_KEY:latest,SUPA_TABLE=SUPA_TABLE:latest \
  --no-allow-unauthenticated
```

*Option B: Deploying an Existing Image*
```bash
gcloud run deploy autobilling-service \
  --image asia-northeast1-docker.pkg.dev/PROJECT_NAME/cloud-run-source-deploy/autobilling-service:latest \
  --region asia-northeast1 \
  --service-account SERVICE_EMAIL_ACCOUNT_HERE \
  --set-secrets GENAI_KEY=GENAI_KEY:latest,SUPA_URL=SUPA_URL:latest,SUPA_KEY=SUPA_KEY:latest,SUPA_TABLE=SUPA_TABLE:latest \
  --no-allow-unauthenticated
```

### 3.2.1 Google Apps Script One-Time Setup
Configuring the Google Apps Script is only required during the initial setup to connect Google Drive with your Cloud Run instance. It is not required for deploying subsequent revisions of the backend.

**Google Cloud Platform (GCP) Project Link**
Apps Script projects use GCP to manage authorizations, advanced services, and other details. You must link the Apps Script to your GCP project using the **Project Number**. To learn more, visit [Google Cloud Platform](https://developers.google.com/apps-script/guides/cloud-platform-projects).

**1. `appsscript.json` (Manifest / JSON Auths)**
Ensure your Apps Script manifest includes the appropriate OAuth scopes and dependencies:
```json
{
  "timeZone": "Asia/Tokyo",
  "dependencies": {},
  "exceptionLogging": "STACKDRIVER",
  "runtimeVersion": "V8",
  "oauthScopes": [
    "https://www.googleapis.com/auth/script.external_request",
    "https://www.googleapis.com/auth/cloud-platform",
    "https://www.googleapis.com/auth/drive"
  ]
}
```

**2. `Code.gs` (Apps Script Functions)**
The core Google Apps Script code requires four configuration variables to be customized:
- `SCANNED_FOLDER_ID`: The Google Drive Folder ID where the scanner uploads new PDFs.
- `ARCHIVE_FOLDER_ID`: The Google Drive Folder ID where processed PDFs are moved to prevent duplicate processing.
- `APP_URL`: The full URL to your Google Cloud Run instance's `/webhook` endpoint.
- `SERVICE_ACCOUNT`: The email of the service account used to authenticate with Google Cloud IAM.

**Core Functions in the Script:**
- `processScannedFolder()`: Scans the specified folder for new files, extracts their metadata (ID, Name, MimeType), moves the processed files to the Archive folder, and packages the metadata into a JSON payload to send to the backend.
- `sendToCloudRun(payload)`: Generates an identity token using the service account credentials and sends the payload to the Cloud Run instance via a POST request.
- `TokenTester()`: A diagnostic utility to manually run and verify if the Google OAuth token generation succeeds.
- `generateFileJsonPayload()`: A helper function that formats and logs a simulated JSON payload from the Archive folder files. This is useful for capturing a payload to test the backend locally using curl.

> [!WARNING]  
> Cloud Build has storage limits on its free tier. Ensure you have applied a cleanup policy (e.g., keeping only the last 2 versions via `gcloud artifacts repositories set-cleanup-policies`) to avoid unnecessary Google Cloud storage costs.

### 3.3 Setting up the Dashboard
The dashboard allows users to view the parsed invoices and mark them as paid.

**Via Antigravity Agent:**
- You can simply type `/setup` to initiate the installation and configure environment variables.
- Type `/run` to boot up the Next.js development server.

**Manual Setup:**
1. Open a terminal and `cd dashboard`.
2. Run `make setup` (or `npm ci`) to install dependencies.
3. Copy `.env.example` to `.env.local` and populate the necessary Supabase credentials:
   - `SUPA_URL`
   - `PUBLIC_SUPA_ANON_KEY`
   - `SUPA_DATA_TABLE_NAME`
   - `SUPA_MASTERLIST_TABLE_NAME`
4. Run `make dev` (or `npm run dev`) to start the server. 
5. Access the application in your browser at `http://localhost:3000`.

> [!TIP]
> The Next.js dashboard uses a `Makefile` for simplified commands. You can also run `make clean` to remove `node_modules` and the `.next` build cache for a fresh restart.
